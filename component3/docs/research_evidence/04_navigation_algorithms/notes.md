# Navigation algorithms evidence notes

- **Objective:** Implement and verify deterministic single-source-to-destination shortest-path navigation over the Phase 1 simulated supermarket graph.
- **Problem being solved:** Component 3 needs the minimum walking-distance route between two graph nodes before multi-stop shopping-order optimization can be added. Routes must follow walkable edges and use stored metre distances rather than straight-line estimates.
- **Why Dijkstra was selected:** The prototype graph is weighted, undirected, and contains only positive edge distances. Dijkstra therefore provides an exact shortest path without model training and exposes pairwise distances that can later support Held-Karp multi-stop optimization.
- **Methodology:** Load and validate the JSON graph into immutable node, edge, and sorted-adjacency structures. Traverse it with a min-priority queue. Store the best accumulated edge distance and full node sequence for each reached node. For exactly equal costs, select the lexicographically smaller complete sequence to make results deterministic.
- **Graph representation:** `StoreGraph` exposes a read-only node mapping, immutable edge tuple, deterministic neighbor tuples, node lookup, and edge-weight lookup. The loader preserves all existing JSON node IDs, inserts both adjacency directions for every edge, and rejects duplicate IDs, unknown edge references, self-loops, duplicate undirected edges, and non-positive weights. The 20-node map is read from `data/store_map/store_graph.json`; it is not duplicated in Python source.
- **Inputs and outputs:** `dijkstra_shortest_path(graph: StoreGraph, start_node_id: str, destination_node_id: str) -> ShortestPath`. `ShortestPath.node_ids` is the ordered node-ID tuple and `ShortestPath.total_distance_m` is the sum of stored graph-edge weights in metres. Unknown endpoints raise `UnknownNodeError`; disconnected endpoints raise `UnreachablePathError`; start equal to destination returns one node at 0 m.
- **Time complexity:** Conventional Dijkstra traversal with a binary heap is `O((V + E) log V)` for a sparse graph. Deterministic full-path tuple comparison introduces a small additional cost when equal-distance alternatives are compared. Space is `O(V + E)` plus stored route tuples.
- **Implementation details:** Implemented `StoreNode`, `StoreEdge`, `StoreGraph`, `GraphValidationError`, and `load_store_graph` in `navigation/store_graph.py`; `ShortestPath`, endpoint exceptions, and `dijkstra_shortest_path` in `navigation/dijkstra.py`; a reusable CLI in `navigation/dijkstra_demo.py`; 15 standard-library tests; and JSON-driven route visualization in `data/store_map/visualize_dijkstra_routes.py`. The algorithm never modifies the graph.
- **Tools and libraries:** Python 3.14.0 standard library (`dataclasses`, `heapq`, `json`, `pathlib`, `types`, `unittest`, and supporting modules); existing standard-library SVG generator; installed macOS Quick Look renderer. Baseline Git commit: `032b26b751c54cf928bee1db603bd1e0f5e5772c`. No dependency was installed and no ML framework was used.
- **Test procedure:** Run `python3 -B -m unittest -v backend.comp3_reco_navigation.tests.test_dijkstra`; run `python3 -B -m backend.comp3_reco_navigation.navigation.dijkstra_demo --output evaluation/comp3/logs/dijkstra_demo.txt`; generate figures with `python3 -B data/store_map/visualize_dijkstra_routes.py`; run the store-map and evidence validators; then run `git diff --check`.
- **Test cases:** Entrance-to-checkout; entrance-to-aisle checkpoint; route between aisle checkpoints; identical endpoints; invalid start; invalid destination; disconnected graph; equal-cost alternatives; weighted-distance choice; consecutive-edge validity; graph immutability; repeated-run consistency; actual graph count/undirected-edge loading; invalid edge reference; and non-positive weight rejection.
- **Observed results:** At 2026-10-13 23:14:48 +05:30, all 15 tests passed with zero failures and zero errors. The reported unittest runtime was 0.001 s. The CLI calculated `ENT -> B4 -> B5 -> CHK` at 8.69 m, `ENT -> B4 -> B3 -> B2 -> B1` at 13.80 m, and `ENT -> B4 -> B5` at 6.60 m. Three 1700×1120 route figures were generated from these actual results and visually inspected. Final verification also passed all 15 Phase 1 store-map checks, validated eight indexed evidence artifacts, and produced no `git diff --check` findings.

Reused the verified Phase 1 renderer fallback and generated all three figures from the implemented algorithm rather than drawing paths manually. Updated the evidence registration helper to write LF line endings so later Git whitespace checks remain clean.
- **Limitations:** Dijkstra solves one start/destination pair and does not optimize the order of multiple shopping stops. Edge weights are static simulated distances with no congestion, turn penalties, accessibility constraints, or live position correction. The current map is connected, so unreachable handling is verified on a separate controlled graph fixture. Hardware localization, AprilTag detection, route deviation handling, and customer movement are outside this phase.

## Phase 6A — interactive offline navigation dashboard foundation

- **Objective:** Provide an offline browser demonstration of the existing Component 3 store graph and deterministic route-planning algorithms without connecting physical trolley hardware.
- **Architecture:** `simulations/navigation_dashboard/` contains a standard-library localhost HTTP server, a typed map/route adapter and demonstration session, bundled HTML/CSS/JavaScript/SVG, and `unittest` coverage. The server exposes only local static assets and `/api/map` and `/api/route`; it binds to `127.0.0.1` by default and rejects non-loopback hosts.
- **Map and routing method:** The adapter loads `data/store_map/store_graph.json` and `data/store_map/apriltag_layout.json`. The browser renders the existing metric node coordinates and edges with equal x/y scale, mapped section labels, entrance/checkout, and eight tag checkpoints. Selected mapped section access nodes are ordered with the existing Held-Karp optimizer and each leg is expanded by the existing Dijkstra shortest-path implementation. The adapter verifies the expanded route distance against the optimizer result. It does not duplicate either routing algorithm or add map geometry.
- **Interaction:** The deterministic default selects B1, B3, and B5. Users can select mapped aisle/category access nodes, calculate a route, clear the selection, or reset the demonstration. Empty selection routes from ENT directly to CHK. Duplicate destinations are stably deduplicated; invalid and unreachable nodes produce an explicit error without replacing the last valid session plan.
- **Observed map data:** The loaded graph contains 20 nodes and 29 edges; the mapped boundary is 24 m by 18 m. The map contains six section access choices and no product-to-location mappings. The AprilTag layout supplies eight checkpoint markers. These are existing map records, not dashboard-created classes, product IDs, or hardware observations.
- **Reproducibility:** From the repository root run `python3 -B -m component3.simulations.navigation_dashboard.dashboard`, then open `http://127.0.0.1:8765/`. The default B1/B3/B5 route produced the actual graph distance 30.29 m and ended at CHK. Clearing selection produced the actual entrance-to-checkout route at 8.69 m. Adapter tests run with `python3 -B -m unittest -v component3.simulations.navigation_dashboard.tests.test_adapter`.
- **Dependencies and limitations:** The dashboard server and adapter use Python's standard library and existing Component 3 algorithms; browser assets are bundled. Streamlit and Plotly were absent from the available environment, so no package was installed. The interface is a static route-planning foundation only: no continuous movement, sensor streaming, or deviation-triggered animation is implemented. Map positions are prototype design values, not a surveyed physical store.
- **Evidence:** `C3-DASH-001` is the live dashboard overview; `C3-DASH-002` the actual graph visualization; `C3-DASH-003` the selected mapped stops; `C3-DASH-004` the calculated route view; `C3-DASH-005` the route summary; `C3-DASH-006` the adapter test output.
- **Research relevance:** This foundation makes the previously verified route algorithms and map inspectable to a panel without claiming physical localization, CNN recognition, or hardware accuracy. It is a separate presentation surface and does not change the navigation algorithms.

## Phase 2B — Held-Karp multi-stop route optimization

- **Problem statement:** A shopping session can require several aisle checkpoints. Applying point-to-point routing to the customer's entered order does not establish that the complete trip is minimal, while allowing the optimizer to change the entrance or final checkout would violate the navigation workflow.
- **Why multi-stop optimization is needed:** The route planner must keep `ENT` and `CHK` fixed while selecting the least-distance ordering of every unique required shopping stop. The optimized order can avoid repeated traversal of the same aisle corridor and supplies an exact benchmark for later scalable routing strategies.
- **Relationship to Dijkstra:** Held-Karp operates on a metric closure of the relevant locations. Every closure distance and every expanded route segment is produced by the existing deterministic `dijkstra_shortest_path` function over stored graph-edge weights. Coordinates and straight-line distances are not used by the optimizer.
- **Methodology:** `held_karp_route(graph, start_node_id, shopping_stop_node_ids, checkout_node_id, *, max_unique_stops=10)` copies the caller's sequence to an immutable tuple, validates every node, removes duplicate stops stably, excludes fixed endpoints from the stop set, computes required pairwise shortest paths, solves the stop ordering with bitmask dynamic programming, and expands the chosen location order back into actual graph nodes. `route_for_stop_order` supplies the reproducible requested-order baseline.
- **Dynamic-programming state:** `DP[mask, j]` stores the minimum distance from the fixed start after visiting exactly the stops represented by `mask` and finishing at stop `j`, together with the ordered visited-stop tuple used for deterministic tie-breaking.
- **Recurrence and termination:** Base states are `DP[1 << j, j] = d(start, j)`. Transitions use `DP[mask, j] = min_k(DP[mask without j, k] + d(k, j))`. The fixed checkout is appended only when selecting the best full-mask terminal state. Equal-distance candidates choose the lexicographically smaller stop order.
- **Complexity and practical limit:** For `n` unique shopping stops, Held-Karp uses `O(n^2 × 2^n)` time and `O(n × 2^n)` DP memory, excluding Dijkstra preprocessing. The configurable default maximum is 10 unique stops. Larger requests raise `StopLimitExceededError`; the implementation does not silently change algorithms or claim unlimited scalability.
- **Interfaces and errors:** The immutable `HeldKarpRoute` result records the original requested IDs, stable unique required IDs, optimized stop order, expanded node route, total metres, start, and checkout. Unknown IDs raise `UnknownNodeError`, disconnected required locations raise `UnreachableLocationError`, and an invalid or exceeded stop limit is reported before DP state allocation.
- **Test methodology:** Eighteen standard-library `unittest` cases cover empty, single, multiple, and duplicate stops; start/checkout included as stops; all invalid endpoint categories; unreachable stops and checkout; deterministic equal-cost tie-breaking; expanded-edge distance and connectivity; input immutability; repeatability; stop-limit enforcement; and optimized distance no worse than requested order. Small controlled cases use an independent exhaustive permutation reference in test code only.
- **Observed sessions:** Session A requested `B1 → B3 → B5` and retained that order: 30.29 m versus 30.29 m, saving 0.00 m (0.00%). Session B requested `B6 → B2 → B4` and optimized to `B2 → B4 → B6`: 37.49 m versus 30.29 m, saving 7.20 m (19.21%). Session C requested `B5 → B1 → B3 → B2` and optimized to `B1 → B2 → B3 → B5`: 44.69 m versus 30.29 m, saving 14.40 m (32.22%). All use fixed `ENT` and `CHK` endpoints.
- **Expanded optimized route:** For all three sessions, the selected graph-node sequence is `ENT → B4 → B3 → B2 → B1 → B2 → B3 → B4 → B5 → CHK`. Revisited nodes are retained because the graph path must follow connected walkable edges.
- **Reproducibility:** From the repository root, run `python3 -B -m component3.backend.comp3_reco_navigation.tests.test_held_karp --output component3/evaluation/test_results/held_karp_tests.txt`; run `python3 -B -m component3.backend.comp3_reco_navigation.navigation.held_karp_demo`; and generate figures with `python3 -B component3/data/store_map/visualize_held_karp_routes.py`. Then run the store-map and evidence validators and `git diff --check`.
- **Limitations:** Results use a static simulated prototype graph, not measured customer or trolley performance. The optimizer does not model congestion, one-way aisles, dynamic obstacles, turn cost, accessibility, product-level locations, live localization, or route deviation. Exponential Held-Karp scaling makes the configured stop cap necessary. Overlapping original and optimized paths in a figure can share the same geometry even when their traversal order and repeated-distance totals differ.
